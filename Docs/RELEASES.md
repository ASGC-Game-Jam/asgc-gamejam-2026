# Release Process

## Start with a version

Before building or releasing a built package, we need to reference an immutable point in our git history.
This makes builds repeatable as anyone reproducing the build will always be looking at the same repository state.

For this project, we use lightweight git tags that follow [semantic versioning](https://semver.org/).

Examples:
* `1.2.0` (stable release)
* `1.3.0-rc1` (pre-release version)

These tags represent immutable points in the git history of our `main` branch and can be referenced as a common
point of knowledge when describing tasks.

## Build the project

Unreal packages can be built from the Editor, or from the UAT command-line tool. At the end of either process, there
will be a folder with a built binary and data files.

### Build with Editor

After checking out the appropriate tagged commit in git, open the project in the Unreal Editor.
To begin building the package, go to `Platforms > Package Project > Package Project` to trigger the default build.
Unreal will ask you what folder you want to output your build to.

You can see the progress of the build in the Output Log.

### Build with UAT

Unreal includes a command-line utility called the Unreal Automation Tool, or UAT. This is used to create packaged builds
without needing to load the full Unreal Editor.

Assuming that your Unreal Engine path, project path and output path are defined as environment variables, a build may look like:
```ps
$env:UE_PATH\Engine\Build\BatchFiles\RunUAT.bat BuildCookRun -project="$env:PROJECT_PATH" -noP4 -platform=Win64 -clientconfig=Development -serverconfig=Development -cook -allmaps -build -stage -pak -archive -archivedirectory="$env:OUTPUT_PATH"
```

There are a lot of options and awesome things that the UAT can do. Please [read the docs](https://dev.epicgames.com/documentation/unreal-engine/unreal-automation-tool-for-unreal-engine?application_version=5.7).

## Smoke tests

It is important to make sure that your build does not fail in basic ways. The first test is always that the packaging
process finishes successfully, but it is always good to do a quick "smoke test" before proceeding with a build. This
usually involves at least opening the built binary to make sure that it loads, and then a simple checklist of basic
functionality (e.g. load main menu, load first level, can run around, quit button works) to ensure that the minimum 
critical path hasn't been accidentally broken, even if the game binary built successfully.

**Do these tests** - if there's smoke, there's a fire that needs putting out before we can release anything.

## Create build artifact

Rather than a folder full of files, it's generally more useful to have a single archive (`.zip` file) that can be
uploaded and attached as needed. This archive file should follow the naming pattern `<project>-<version>-<platform>`
e.g. `ProjectAtlantis-1.2.0-Windows.zip`.

## Make a GitHub Release

Follow [GitHub's release documentation](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
and attach the build archive from the previous step to a [new release](https://github.com/ASGC-Game-Jam/asgc-gamejam-2026/releases/new).

Some tips:
* everything starts from that git tag - make sure you're pointed at the right one
* use release drafts to ensure that you have all assets attached and descriptions before publishing
* use Immutable releases to ensure we aren't rewriting history with our builds (stable or otherwise)

Each GitHub release should be able to have its description auto-generated by GitHub and the `release.yml` template
based on the PRs that have been merged since the last release. Read the description and modify it as needed to ensure
if reflects an accurate changelog.

## Upload to Steam

This is an optional additional step - most users will be able to access the builds from the GitHub releases, but it
may also be convenient to keep the project updated via Steam. Pre-release versions can be uploaded to a `beta`
branch so as to not clutter the main update branch.

### Setup

1. Get the App ID and Depot ID from Steamworks, add these as repository variables on GitHub:
    * `Steamworks > App Admin > ASGC 2026 Game Jam Playtest`
      * The App ID is in parentheses after the name at the top of the page
    * From the above page, `Technical tools > Edit Steamworks Settings`
      * The header will look like: `Steamworks > App Admin > ASGC 2026 Game Jam Playtest > App Data Admin > SteamPipe > Depots`
      * The Depot ID will be listed under `Configuring Depots`
2. Download the latest Steamworks SDK: https://partner.steamgames.com/downloads/list
3. Set up the SDK: https://partner.steamgames.com/doc/sdk/uploading#1
    * The important parts are extracting the SDK somewhere sensible, and running the `steamcmd.exe` once manually to bootstrap the build system
4. Set up the SDK config using the App ID, Depot ID and your Steam user: https://partner.steamgames.com/doc/sdk/uploading#3
    * This should generate `app_<App_ID>.vdf` and `depot_<Depot_ID>.vdf` files in your `tools/ContentBuilder/scripts` folder
    * For the build `desc` field, prefix with the semantic version and an optional description of the build e.g. `1.2.0 - New content levels`

### Upload a build

Before uploading a new build, make sure to:
* update the `desc` field in the app VDF to reflect the new build version
* update the files in the local content root in the depot VDF to be the unzipped game files directory

Uploads are handled via the `steamcmd.exe` utility, with a command similar to:
```
tools\ContentBuilder\builder\steamcmd.exe +login <account_name> <password> +run_app_build ..\scripts\app_<App_ID>.vdf +quit
```

There is a version of this also supplied as a batch file (`run_build.bat`) with the Steam SDK that you can modify to
your own version of this instead of copying the command each time.

If your app VDF has the "preview" flag set to "1", it will do a dry run of the upload process (including logging in with your
credentials and triggering Steam Guard authorization) and will *not* upload the build. This is a useful habit to get into
doing even for a routine build upload to make sure the output makes sense.

Once happy with the dry run output, adjust the "preview" flag to "0" and re-run the `steamcmd.exe` utility command.
